Web で「パララックス」と呼ばれているものは、この一文の実装が四つの軸に分かれて散らばった結果にすぎない。 軸を分けて並べ直すと、効くものと効かないものがはっきりする。

四つの軸

「パララックス」が広義なのは、別々の軸の話が同じ名前で呼ばれているから。 分解すると、各実装がどこに位置しているのかが座標で言えるようになる。以降の各図版には、この四軸での座標を付けてある。

PLATE I

Stellar Parallax

恒星視差 — 視差で距離を測る
観測：地球軌道の両端（基線 2 AU）
星視差 ϖ ["]距離 [pc]距離 [ly]黄緯 β図上のずれ

何を見ているか

地球が軌道を一周するあいだ、星は空の上で楕円を描く。その半軸は ϖ と ϖ·sin β。 黄道の極では真円に、黄道面上では直線に退化する。楕円の大きさは距離の逆数にそのまま比例する。

星をクリックすると、その星の視差楕円が引かれる。ポラリスとベテルギウスはずれが 1px を切って測れない — 地上観測の限界 100 pc がそのまま図に出る。

なぜこれが「高度」か

他の五つが視差を装飾に使っているのに対し、これだけは視差を計測に使っている。 動きが数値を生み、数値が意味を持つ。パララックスが飾りに見えてしまう問題の、唯一の根本解。

Web への転用

「奥行き＝情報の階層」に読み替える。ブランドマークは遠く（動かない）、CTA は近く（大きく動く）。 動きの量が重要度の宣言になるので、装飾ではなく情報設計として正当化できる。

ϖ [arcsec] → d [pc] = 1 / ϖ Δx = −ϖ·sin(θ) Δy = −ϖ·cos(θ)·sin β 半軸 = ϖ, ϖ·sin β ／ 1 pc = 3.26 ly

PLATE II

Depth Stack

深度層 — 大気遠近を足す
枠の中をスクロール
↕ scroll
手がかり

手がかりを一つずつ外してみる

「速度差」だけ残して他を全部切ると、層が動いているだけで奥に見えない。これが世の中のパララックスの大半の状態。 「遮蔽」を切ると最も派手に崩れる — 手前が奥を隠すことが、単眼の奥行き手がかりとして最も強い。

知覚科学的にも、運動視差は単独では弱い単眼手がかりで、他の手がかりと足し算して初めて効く。 両眼視差と併用すると 3D 構造の検出閾値が平均 48% 下がる、という測定がある。

単一の深度値から全部を導く

速度・ぼけ・彩度・コントラスト・スケールを別々に手で調整すると必ずずれる。 z ひとつを入力とする関数にして、そこからすべてを導出する。これが実装上の要点。

Web への転用

転用性は 6 案で最高。既存のヒーローに --depth トークンを足すだけで載る。 層は 3〜4 枚が上限。それ以上は速度差を知覚できず、合成コストだけ払うことになる。

z ∈ [0,1]（0=手前, 1=奥） speed = 1 − 0.72·z blur = 3.2px · z^1.6 sat = 1 − 0.55·z scale = 1 + 0.06·z （本文の背後なら speed は 0.8〜1.2 に留める）

PLATE III

Inversion

逆視差 — 符号を反転させる
正常 → 奥行き消失 → 反転
↕ scroll
奥が速く動きはじめると、風景が裏返る

意図的に規則を破る

「近いものほど速く動く」を途中で反転させると、シーンが内側に裏返る。 凹んだ仮面が凸に見えるホロウマスク錯視の、運動視差版。脳が奥行きの符号を決めかねて、画面がひっくり返り続ける。

実装は sign を掛けるだけで、コストはほぼゼロ。にもかかわらず、ほとんど誰もやっていない。

Web への転用

ページ全体には使えない。一箇所だけ、章の切れ目や 404、意図的に居心地を悪くしたい瞬間に。 「境界を硬くする」を押すと不快さが跳ね上がる — 演出の強さと安全性が真正面から衝突する例として見てほしい。

PLATE IV

Off-axis Window

覗き窓 — 視錐台を組み直す
図の上でポインタを動かす（タッチ可）
A ／ 平行移動（よくある実装）
B ／ 非対称視錐台（正しい投影）
同じ立体・同じ視点入力。違うのは投影だけ

A と B の違い

A は層を深度に比例して平行移動しているだけ。奥の面は形を変えない。動いてはいるが、 穴を覗いている感じにならない。B は視点位置からスクリーン平面へ光線を張り直しているので、 奥の壁がせん断して手前の枠に隠れる — 遮蔽と透視が同時に成立する。

数学は光線とスクリーン平面の交点を取るだけで、これが Kooima の generalized perspective projection （非対称視錐台）と同じもの。行列を組まなくても、この 3 行で足りる。

THREE.js を使わないことの証明

点と線だけなら投影は自前で書けて、出力は 1px の正確な線になる。 WebGL の lineWidth がほぼ 1px 固定でアンチエイリアスも効かない問題を、そもそも踏まない。 製図・計器の美学とは相性が最初から良い。

拡張

視点入力をポインタから webcam の頭部位置（MediaPipe Face Mesh）に差し替えると、画面が本当に壁の穴になる。 Johnny Lee の Wii リモコン頭部追跡をブラウザでやり直した実装が既にいくつかある。投影側のコードは一切変わらない。

eye = (ex, ey, ez) ez > 0（画面の手前） P = (px, py, pz) pz < 0（画面の奥） t = ez / (ez − pz) sx = ex + (px − ex)·t sy = ey + (py − ey)·t

PLATE V

Velocity Parallax

速度視差 — 位置ではなく遅れで深度を出す
勢いよくスクロールして、止めてみる
↕ 勢いよく

オフセットではなく遅れ

深度を位置のずれではなく追従の遅れで表現する。層ごとに剛性の違うばねを持たせ、 奥ほど柔らかくする。スクロールを止めても、奥の層はまだ沈み続けている。

スクロール速度そのものを可視化しているので、止まっている状態では視差が完全に消える。 これは大きな利点で、読んでいる最中は画面が静止する。

Web への転用

画像が一切なくてもタイポグラフィだけで成立する。写真素材を持たない編集系・テキスト主体のサイトで、 唯一使えるパララックス。GSAP なら ScrollTrigger.getVelocity() をクランプして power3 で 0 に戻すのが定石。

A — 3D 空間に置いて縮尺で戻す

スクロールコンテナに perspective を置き、層を translateZ で奥へ送る。 奥へ送ると小さくなるので、縮尺で戻す。この補正式が全て。ブラウザが視差を勝手に付けてくれる。

B — スクロールをタイムラインにする

animation-timeline: scroll() でスクロール位置をアニメーションの再生位置に直結する。 view() なら要素の可視範囲基準、animation-range で区間を切り、 timeline-scope で DOM 上無関係な要素どうしを同じタイムラインに繋げる。

現在地（2026-08）

Safari 26 が 2025 年 9 月に対応、Chrome / Edge は 115+。Firefox は安定版でまだフラグ裏で、 Interop 2026 の優先項目。グローバル約 84%、Baseline 未達。 ポリフィルはメインスレッドに落ちるので性能利点が消える — 入れる意味がない。

結論は素直に CSS を本命・GSAP をフォールバック。両方コンポジタスレッドで走るので、 どちらに転んでもメインスレッドは空く。

3–4

深度面の上限

これを超えると速度差が知覚できなくなり、合成コストだけが増える。奥行きは少数の層の明確な分離から生まれるので、多数の層をわずかずつ動かしても出ない。

0.8–1.2

本文背後の速度比

0.3〜1.7 まで開いてよいのは純装飾レイヤーのみ。本文の背後で速度差を広げると可読性が落ち、酔いを誘発する。

2.3.3

WCAG

2.3.3（AAA）はインタラクション由来のアニメーションを無効化できることを要求。2.2.2（A）は 5 秒を超える動きに停止手段を要求。パララックスは前庭障害のトリガーとして名指しで挙がる典型。

2

動かしてよいプロパティ

transform と opacity だけ。top / margin / background-position を動かした時点で毎フレーム再レイアウト・再ペイントが走る。

✕

background-attachment: fixed

最も安く書けて最も重い。スクロールのたびに再ペイントされる。CSS 3D か scroll-timeline に置き換える。

1
